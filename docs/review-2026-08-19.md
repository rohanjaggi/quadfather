## A. New findings (not in `improvements.md`)

### A1. Critical

**A1.1 Step-calorie formula credits ~2.8 kcal per extra step (≈70× too high)**
`src/lib/steps.ts:28-30`, duplicated client-side `src/app/analytics/page.tsx:970-972`
```ts
const extraSteps = Math.max(0, todaySteps - baseline)
const stepCalories = extraSteps * 0.04 * weight     // 0.04 is already kcal/step for ~70 kg
```
Walking ≈ 0.04 kcal/step *total* (~0.0005–0.0007 kcal/step/kg). Multiplying by weight again gives 2.8 kcal/step at 70 kg. A 75 kg `moderately_active` user at 10 000 steps gets `3000 × 0.04 × 75 = 9 000 kcal` added to `budget.steps_credit` / `macros.calories.goal` (`users/me/route.ts:55-61`), the daily-coach prompt, and the analytics "Extra Calories Earned" card. Has been this way since the feature was added (`e5b4569`). If you haven't noticed, it's because steps rarely exceed baseline or the Shortcut isn't syncing — check a high-step day.
→ `extraSteps * 0.04 * (weight / 70)` (or `* 0.00057 * weight`); export one function and delete the analytics copy.

**A1.2 Webhook handler hits grammY's 10 s default timeout → Telegram re-delivers → duplicate logs and AI spend**
`src/app/api/webhook/[secret]/route.ts:17-18`; grammY 1.42 defaults verified in `node_modules/grammy/out/convenience/webhook.js:64` (`onTimeout = "throw"`, `timeoutMilliseconds = 10000`).
```ts
const handleUpdate = webhookCallback(getBot(), "std/http");
return handleUpdate(request);          // also: not awaited inside the try → catch never sees rejections
```
Photo / `/log_meal` / `/coach` / `/insights` do file download + LLM call + DB write — routinely >10 s. grammY rejects, Next returns 500, Telegram retries the same update, and `prisma.foodLog.create` (`telegram-bot.ts:288,589`) runs again.
→ `webhookCallback(getBot(), "std/http", { timeoutMilliseconds: 55_000, onTimeout: "return", secretToken: WEBHOOK_SECRET })` + `export const maxDuration = 60`; `return await handleUpdate(request)`. Better: ack 200 immediately and process via `waitUntil`.

**A1.3 `updateProgressAfterWorkout` runs twice per workout (and races)**
`src/app/api/workouts/route.ts:77-79` (fire-and-forget) and `src/app/api/workouts/[id]/analyse/route.ts:33` (awaited). `RecentWorkouts.tsx:74` renders `<WorkoutAnalysis>` for every workout without `analysis`, whose `useEffect` (`WorkoutAnalysis.tsx:23-33`) POSTs `/analyse` immediately after logging. In `progress.ts:153,185`:
```ts
const improved = best1RM > existing.estimated_1rm          // 2nd call: equal → false
sessions_since_improvement: improved ? 0 : existing.sessions_since_improvement + 1,
```
Second call sees `best1RM === existing.estimated_1rm` → `prs` empty (so the AI analysis / Telegram PR message systematically misses PRs) and `sessions_since_improvement` is **incremented on a PR session**. If the two overlap, both read the same `existing` → double increment, or both `create` a new snapshot → P2002 → `/analyse` 500. Every AI failure re-triggers the mutation on next render; old un-analysed workouts re-apply their sets to current snapshots.
→ Make it idempotent (record last applied workout id on the snapshot, or derive PRs from history), call it exactly once (awaited in POST, or `waitUntil`), and have `/analyse` read stored PRs.
